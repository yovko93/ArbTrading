# Local access and storage

The local OS account is the trust boundary. A cryptographically random 256-bit credential is created for each backend process. The backend writes it with its loopback address into `runtime/connection.json` only after the database is initialized and HTTP startup succeeds. There is no credential-returning endpoint. Credentials are never supplied in configuration, URLs, arguments, response bodies, or log messages.

Windows runtime directories have protected DACLs granting only the current account FullControl with child inheritance. The credential file also has an explicit current-user owner and protected DACL. Unix directories use 0700 and credential files use 0600. Symlinks/reparse points are rejected. The desktop verifies permissions before reading; an unsafe or unavailable file produces a visible failure rather than disabling authentication. Atomic replacement avoids partial reads.

Readers allow file replacement. On Windows, publication retries transient replacement failures for at most two seconds, then fails closed; it never deletes the destination first or relaxes permissions. This addresses the observed sharing race and the [reported .NET/Windows overwrite behavior](https://github.com/dotnet/runtime/issues/114230). Overlapping reads/rotation and a short-lived external reader are covered by real-file tests.

The desktop sends `Authorization: Bearer` over literal loopback HTTP, disables proxy use and redirects, and does not log HTTP requests. Re-reading connection metadata on each operation and one retry after 401 support credential rotation. A stopped backend can leave stale metadata; it grants no access once that process is gone. Restart generates a new credential while keeping internal UserIds and WorkspaceIds. Refresh recovers after a restart or after a backend initially being absent. A request interrupted during a write is not automatically retried after a transport failure: its outcome may be uncertain; refresh to inspect actual state.

This mechanism does not protect against an administrator or a fully compromised process running as the same OS user. It is not remote authentication, does not establish a public user account, and must not be exposed by port forwarding or a reverse proxy. All local clients possessing the credential map to the same persisted local owner. No Windows username, machine name, email, or client-supplied UserId establishes application identity.

The sole supported host binding option is `Local:BaseUrl`: HTTP with a literal loopback address and a port of 1024–65535. Host `urls`, HTTP/HTTPS port environment overrides, and Kestrel endpoint configuration are rejected. Kestrel listens explicitly on the validated IP. Server deployment and non-Paper mode configuration fail startup. No CORS middleware, exchange credential endpoint, user-creation endpoint, or test authentication bypass exists.

Every business endpoint requires authentication, and workspace operations explicitly join membership with the requested workspace. Writes check Owner membership inside the transaction and commit the name and audit together. Forbidden and absent workspaces both return 404 to avoid revealing existence. Audit contains server-resolved actor, resource workspace, exact UTC instant, action, and a server-generated correlation ID. Unknown fields in mutation DTOs are rejected; identity headers and query parameters do not supply claims.

Each backend holds exclusive file handles for both its data and runtime directory. A second backend cannot reuse either location. This also prevents distinct data directories from racing to replace a shared credential file. Each request uses a scoped DbContext; there is no global mutable actor/workspace. The desktop has no reference to Infrastructure or the database.

Logs contain structured operational states and bounded retention (seven files per process, at most 5 MB per file, rolling daily/by size). Raw exceptions, request bodies, authorization headers, and credentials are not logged. Logging is configured in code to avoid accidentally enabling HTTP header capture. Database failures return unavailable/503, not an in-memory success. The anonymous liveness response is not a persistence-health assertion.
