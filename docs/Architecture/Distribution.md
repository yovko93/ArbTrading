# Portable distribution architecture (D01 / D02)

The Windows x64 ZIP contains separate self-contained Release publishes: net10.0-windows WPF Desktop at the root and net10.0 ASP.NET Backend under `backend/`. Both carry their runtime; publish explicitly disables trimming, NativeAOT and single-file bundling. Desktop still references Contracts only and reads business state through authenticated HTTP. No installer, runtime installation, updater or capability changes are involved.

```
ArbitrageTrading/
  Arbitrage.Desktop.exe
  [Desktop assemblies and self-contained runtime]
  backend/
    Arbitrage.Backend.exe
    appsettings.json
    [Backend assemblies and self-contained runtime]
  distribution-manifest.json
  README-FIRST-RUN.txt
```

D01 manifest schema 1 records Product, RuntimeIdentifier, TargetFrameworkDesktop/Backend, SourceCommit, SourceDirty, UTC BuildUtc, PackageMode, relative Desktop/Backend/BackendConfig paths and SHA-256 values, plus a Files map covering every payload file except the manifest itself. ExpectedTradingMode is descriptive only. Source identity is embedded at build time; runtime never invokes git. ZIP SHA-256 is external. These checks detect corruption, not malicious replacement of both files and unsigned manifest.

Backend selection is explicit absolute ARBITRAGE_BACKEND_ARTIFACT, packaged backend executable, then legacy adjacent development executable. Presence of the manifest or packaged backend directory selects the package safety boundary. Packaged Start requires a valid manifest and that the selected executable is the manifest's fixed backend path; overrides cannot bypass integrity. Relative/rooted/traversing paths, reparse points, unexpected/missing files, hash mismatches and unsafe config fail closed. Missing manifest remains supported only for development layouts. Invalid package status remains visible in Settings; Start cannot launch it. `Arbitrage.Desktop.exe --validate-package` exits 0 for valid packages, 2 otherwise, and never starts a backend.

Settings shows package mode, manifest state, RID, source/dirty identity, build instant, data/runtime locations and last database startup result. The initial scan is cached for display; explicit Start rescans before migration and before normal launch. These checks are not a code-signing substitute and do not protect against an attacker concurrently rewriting an executable after validation.

Desktop launch and Refresh only observe. Explicit packaged Start takes the existing desktop launch lock, checks ownership and port availability, validates package/storage, executes the packaged backend with `--migrate`, awaits successful exit, revalidates, then starts it normally. Both processes receive identical absolute data/runtime paths, loopback URL and pinned Local/Paper/ManagedLocal settings. No migration process runs concurrently with the normal process started by this operation. The backend's LocalRuntimeLease still excludes other processes using that profile. Failure, cancellation or timeout prevents normal launch. Only a timed-out migration child owned by this operation may be terminated. Normal Start/Stop ownership metadata continues binding instance, profile, workspace, executable, PID and start time. Closing Desktop leaves a running backend intact.

Under the lease, an existing database with pending migrations is copied using SQLite BackupDatabase, including committed WAL state. The backup passes integrity_check and private-file verification before becoming a completed `.db` backup. Failed copies remain `.pending` evidence and are never mistaken for completed backups. Latest five completed backups are retained under `backend/backups/schema`, named with UTC time and GUID. Retention failure blocks migration. There is no backup for new/current schema. Unknown migration IDs fail as UnsupportedNewerSchema before backup or mutation. Manual normal backend launch retains explicit-migration refusal. Migration failure never deletes/resets the database or auto-restores a backup; operators preserve state for recovery.

Mutable state remains under the current OS user's LocalAppData/ArbitrageTrading: backend database/logs/credentials/evidence/backups, runtime connection and ownership metadata, and desktop preferences/logs. Absolute advanced environment overrides remain supported; package-local mutable storage is rejected. Desktop validates its own storage before writing. Backend validates configuration and protected storage independently. Package appsettings contains only Local/Paper/loopback defaults. Environment overrides precede appsettings; existing nonloopback, mode, ownership and authorization restrictions remain. No user profile, bearer credential, exchange key or database is copied into a package.

The canonical PowerShell 7.5+ publisher requires Windows x64, records commit/dirty identity, verifies source by default, publishes into a unique repository artifacts staging directory, scans for runtime/secret files, checks hashes/runtime configs, archives and tests an extracted copy outside the checkout. Default requires clean source. `-AllowDirty` produces an explicitly local-dirty ZIP. `-SkipTests` requires CI plus matching verified SHA and clean source; Windows CI supplies it only after successful verify.ps1 in the same job. Linux verification is unchanged. No build step migrates normal user storage or publishes a release.


## D02 Authenticode layer

The canonical publisher accepts explicit `Unsigned` (default), `Authenticode`, and `TestEphemeral` modes. Signing is confined to the newly created staging tree after publish/removing development files and before inventory hashing. Every signature is verified before the schema-2 manifest records final bytes. Package validation precedes creation of a temporary smoke archive; only successful extracted smoke promotes that archive to the final ZIP and external SHA-256. Signing may change bytes/timestamps, so signed packages are not claimed byte-for-byte reproducible. Source SHA, InformationalVersion, RID and Paper capabilities are preserved.

The exact signing allowlist is shared by tooling/runtime: `Arbitrage.Desktop.exe`, `Arbitrage.Desktop.dll`, `Arbitrage.Contracts.dll`, and under `backend/`: `Arbitrage.Backend.exe`, `Arbitrage.Backend.dll`, `Arbitrage.Contracts.dll`, `Arbitrage.Domain.dll`, `Arbitrage.Application.dll`, `Arbitrage.Infrastructure.dll`, `Arbitrage.Connectors.dll`, `Arbitrage.Execution.dll`, `Arbitrage.Strategies.dll` (12 paths). Microsoft/.NET and third-party DLLs retain their original signatures/bytes.

`distribution-signing.ps1` owns the provider boundary; CI contains no SignTool commands. Production selects an existing, current code-signing certificate with a private key from CurrentUser/My by exact thumbprint. It discovers Microsoft-signed SignTool from versioned Windows SDK x64 directories or a trusted absolute SIGNTOOL_PATH outside staging. SignTool uses SHA256 file digest, HTTPS RFC3161 timestamping with SHA256 timestamp digest, and `/pa /all` verification. Production requires clean source, no AllowDirty, certificate configuration and a timestamp URL without embedded credentials. There is no unsigned fallback. PFX import/export, certificate procurement and cloud providers are not implemented. A future provider can replace the signing operation behind this boundary without changing publisher sequencing.

TestEphemeral uses Windows Set-AuthenticodeSignature with SHA256 and a dynamically generated, eight-hour, non-exportable RSA code-signing identity in CurrentUser/My. This deliberate test provider works without SignTool and uses no timestamp network service. It does not install roots or publishers. The exact certificate and CNG private key are deleted in finally, with certificate-store and key-file absence verified even after a signing failure. Only its public subject/thumbprint are reported or embedded. It never qualifies as production trust.

Schema 2 adds SigningRequired and Signing { Mode, Status, PublisherSubject, CertificateThumbprint, SignatureAlgorithm, Timestamped, RequireTimestamp, Files }. Unsigned has SigningRequired=false and UnsignedSnapshot status; Authenticode requires signing/timestamp and labels SignedSnapshot; TestEphemeral requires structured test signatures and labels TestSignatureOnly. D01 schema 1 is still recognized as LegacyUnsigned. Mode/required/timestamp policy combinations must agree. Status/publisher strings in JSON do not establish Windows trust.

The shared C# AuthenticodeVerifier calls WinVerifyTrust with the generic Authenticode policy and a separate content/hash verification. It reads the native signer/certificate evidence, enforces SHA256 and expected identity, and checks timestamps. Tooling and Desktop use the same implementation. Runtime verification suppresses UI and network retrieval and uses local Windows trust/cache without online revocation checks; it cannot report fresh revocation status or guarantee that a new issuer chain is cached. Production signature validity therefore means valid under the local offline Windows policy, not public reputation certification. Publishing additionally requires SignTool verification. No runtime PowerShell, SDK or signing tool is required by the ZIP.

Package validation checks paths, inventory, final hashes, then independent signatures for all 12 targets. Required signatures that are missing/invalid/mismatched prevent managed Start. Unsigned snapshots remain supported and explicitly labeled. Test mode permits only intact untrusted signatures with the expected test identity and conspicuous test wording; it is never promoted to Authenticode production validity. Settings reports mode/required policy, actual Desktop/backend signature states, actual publisher and timestamp separately from package hashes, connectivity and trading availability. As with D01, an unsigned manifest is not an authenticated policy authority: local replacement of both the application and policy is outside this corruption/inspection boundary.

Default PR/push CI uses windows-latest, unsigned main artifacts, and a separate ephemeral canonical signing exercise that is not uploaded as the main download. Production requires an explicit repository switch on push to main only. A pre-provisioned protected signing runner can be selected for that path; arbitrary PRs never select that runner or receive signing-step inputs. Token permissions remain contents: read. No release is published.

SHA256 detects changed bytes; Authenticode binds executable content to a signer; RFC3161 timestamps support certificate-expiry validation under Windows rules. SmartScreen/Edge reputation is separate. The ZIP itself is not Authenticode-signed, and signed EXEs do not guarantee that browser/Defender reputation warnings disappear. D03 defers installers, MSIX/MSI/WiX decisions, Start Menu/uninstall/Program Files integration, release channels and auto-update.

Primary references consulted: [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool), [WinVerifyTrust](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust), and [WINTRUST_DATA offline policy flags](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_data).
