# Phase 02A public exchange integration

Verified against official documentation on 2026-09-22:

- [Polymarket Discover Markets](https://docs.polymarket.com/market-data/discover-markets) and [Market Details](https://docs.polymarket.com/market-data/market-details).
- [Kalshi Market Data Quick Start](https://docs.kalshi.com/getting_started/quick_start_market_data) and [Get Markets](https://docs.kalshi.com/api-reference/market/get-markets).

The catalog adapters use fixed production HTTPS hosts and dedicated unauthenticated clients. No local bearer credential, exchange account credential, proxy rotation, or arbitrary URL fetch is involved. The desktop talks only to its authenticated local backend. Phase 02B.1 adds separate public orderbook clients, described below.

Polymarket uses `GET https://gamma-api.polymarket.com/markets/keyset?closed=false&limit=100`; each `next_cursor` is passed unchanged as `after_cursor`. This covers publicly enumerable markets whose Gamma `closed` filter is false, without selecting a tag/category or excluding negative-risk markets. The raw Gamma envelope is `{ markets: [...], next_cursor: ... }`. Raw `outcomes` and `clobTokenIds` are JSON-encoded arrays; the adapter parses both and correlates by index only when lengths match. This differs from SDK-normalized `outcomes.yes`/`outcomes.no` objects. Missing tags, event references, and token arrays remain missing with warnings. `active` and `acceptingOrders` are retained as native state; normalized labels are conservative and do not claim trading readiness. `startDate`, `endDate`, `closedTime`, and `updatedAt` remain distinct.

Kalshi uses `GET https://external-api.kalshi.com/trade-api/v2/markets?status=<scope>&limit=200`, traversing `unopened`, `open`, `paused`, and `closed` separately. A returned opaque `cursor` is passed unchanged as `cursor`. The public endpoint is unauthenticated. The raw envelope is `{ markets: [...], cursor: ... }`. Native `ticker`, `event_ticker`, `mve_collection_ticker`, `market_type`, `status`, `rules_primary`, `rules_secondary`, and source timestamps are preserved where returned. The listing does not provide series category or tags, so those remain unknown. Kalshi outcome labels Yes/No have no fabricated token IDs. No `mve_filter=exclude` is applied, preserving listed multivariate markets. No incompatible `min_updated_ts` filter is used.

The Kalshi quick start mentions `status=all`, while the endpoint reference lists only `unopened`, `open`, `paused`, `closed`, and `settled` and says an empty status returns any state. The adapter uses the four explicit non-finalized filters instead of relying on the quick-start shorthand or paging through historical settled markets.

For both exchanges, a page's continuation cursor controls traversal even when the page is short. A repeated cursor or several non-progressing pages fails the run. Records are keyed by exchange plus native ID, stored per page, and never deleted due to a partial or failed run. Complete means reaching the end of every selected scope during this run, not an atomic global exchange snapshot. Historical settled backfill and efficient incremental synchronization are deferred.

The backend allows one page request per exchange at a time, paces requests by at least 300 ms by default, bounds each request to 12 seconds and 8 MB, retries safe transient GET failures at most twice, and honors `Retry-After`. `Local:PolymarketRequestIntervalMs` and `Local:KalshiRequestIntervalMs` configure pacing independently from 100–10,000 ms. Default requested page size is 200 (effective Polymarket maximum 100, Kalshi 200) and default run budget is 15 minutes; `Local:DiscoveryPageSize` accepts 1–500 and `Local:DiscoveryRunMinutes` accepts 1–120. Hitting the time budget or a `Retry-After` beyond it yields Partial. A 401/403 public response fails only that exchange run and does not revoke local workspace access. Malformed envelopes fail; malformed records without usable identity are counted. External text and references are displayed as inert text and never fetched automatically. Prices are omitted because listing data is not an executable quote.

Optional sampled live connectivity check, from the repository root:

```powershell
./scripts/smoke-market-discovery.ps1 -Live
```

This makes at most two read-only requests per exchange with a page size of five, following one continuation only when returned. It neither starts a backend nor writes normal user storage; the C# adapter sample verifies parsed records in isolated temporary SQLite and does **not** verify full traversal. To exercise an installation, launch backend and desktop with the isolated paths described in `LocalDevelopment.md`, then explicitly select **Sync Markets**. Polymarket did not produce a parsed response; a separate status-only shell check reported an untrusted TLS certificate chain (`SEC_E_UNTRUSTED_ROOT`). Certificate verification was not bypassed. ## Phase 02A.1 contract correction

[Kalshi's lifecycle documentation](https://docs.kalshi.com/getting_started/market_lifecycle) separates request filter names from REST response statuses: `unopened` selects `initialized`, `open` selects `active`, `paused` selects `inactive`, and `closed` selects markets past close that are not finalized. The adapter maps `initialized` → Upcoming, `active` → Open, `inactive` → Paused, `closed` → Closed, `determined` → Determined, `disputed` → Disputed, `amended` → Amended, and `finalized` → Finalized. Future native values stay Unknown with a warning. Polymarket `closed=true` means trading has closed; it is labeled Closed, never inferred to be finalized. Neither exchange's timestamps prove settlement.

The [Kalshi Get Markets contract](https://docs.kalshi.com/api-reference/market/get-markets) requires a string cursor; the empty string ends paging. The Phase 02A.1 parser accepted a string, null, or omission only with explicit `has_more=false`; Phase 02A.2 replaces that behavior with the dedicated keyset API contract. Unsupported cursor types fail the run. Short pages do not imply termination. The four Kalshi buckets and the `closed=false` Polymarket feed are changing upstream data, never an atomic snapshot. Prior Kalshi runs covering only three buckets do not satisfy current full-coverage metadata.

Test JSON is contract-shaped synthetic data based on those official pages, not a live recording. The opt-in script now calls production C# adapters and stores each sampled page in its own temporary SQLite database. It now issues at most two GETs per exchange with a page size of five and labels the result Sampled. A successful page does not mean Complete coverage. Secure-connection failures stop without ordinary transient retries; the reported classification does not assert a specific certificate-chain cause unless separately observed.

## Phase 02A.2 Polymarket keyset correction

The [official keyset API reference](https://docs.polymarket.com/api-reference/markets/list-markets-keyset-pagination) and [May 14, 2026 changelog](https://docs.polymarket.com/changelog/predictions) set `GET /markets/keyset` to `1 <= limit <= 100`. `Local:DiscoveryPageSize` remains a requested size of 1–500. The Polymarket adapter uses `min(requested, 100)` for **every** outbound keyset request; Kalshi continues to receive the requested size. Cursor traversal continues until the documented terminal response, so a smaller effective page does not impose a total-record cutoff.

The keyset reference says `next_cursor` is omitted on the last page. A valid `markets` array with an omitted cursor ends traversal, whether it contains records or is empty. A present nonempty string is passed unchanged as `after_cursor` even on a short page. Present null, empty string, boolean, number, array, and object cursor values are rejected because this endpoint's reference documents an opaque string when continuation exists and omission at termination. Kalshi's required string cursor and empty-string terminal rule remain separate. The synthetic parser and SQLite tests verify these rules; they are not live recordings.

Production and the optional C# sample share `PublicMarketTransport.CreateHandler()` with redirects and proxy use disabled. Normal certificate and hostname checks remain enabled. The sample makes one attempt per page, follows at most one cursor, caps each page at five records, reports each stage and exchange separately, and exits nonzero if either requested check fails. A parsed empty page is reported as `SampledEmptyParsed`, not evidence of market-record validation. See `Phase02A.2Verification.md` for the actual live result and remaining environment limitation.

- [Kalshi Orderbook Responses](https://docs.kalshi.com/getting_started/orderbook_responses), [Fixed-Point Representation](https://docs.kalshi.com/getting_started/fixed_point_migration), [Get Market Orderbook](https://docs.kalshi.com/api-reference/market/get-market-orderbook), [Get Multiple Market Orderbooks](https://docs.kalshi.com/api-reference/market/get-multiple-market-orderbooks), [API Environments](https://docs.kalshi.com/getting_started/api_environments), [Rate Limits](https://docs.kalshi.com/getting_started/rate_limits), and [Get Markets](https://docs.kalshi.com/api-reference/market/get-markets).

No trust setting was changed. Polymarket fixtures therefore follow the explicit **raw REST** examples on the official Prices and Order Books page, not SDK field names. This is a documented verification limitation.

| Exchange | Implemented GET | Wire data | Interpretation |
| --- | --- | --- | --- |
| Polymarket | `https://clob.polymarket.com/book?token_id=<catalog token>` | `asset_id`, `market` (condition identity), millisecond `timestamp`, `hash`, `bids`/`asks` with string `price`/`size` | Native bid/ask levels for the selected outcome token. Gamma market ID remains separate from condition ID. Returned asset must match requested token. |
| Kalshi | `https://external-api.kalshi.com/trade-api/v2/markets/<catalog ticker>/orderbook?depth=0` | `orderbook_fp.yes_dollars` and `.no_dollars`; pairs of string dollar price and fixed-point quantity | Native YES/NO bids. Polymarket's single-book endpoint documents no depth parameter. Its batch endpoint accepts up to 500 tokens; this implementation deliberately fetches one selected token. Kalshi documents zero depth as all levels and positive depth 1–100 as limited depth. Its multi-book endpoint is not used. Documentation differs on array order; normalization always sorts independently. Kalshi's generated endpoint reference lists authentication headers, while its Orderbook Responses guide explicitly says no authentication is required. The production adapter sends none; the live sample confirmed HTTP 200 without credentials. A future denial is `PublicAccessDenied`, never a trigger to collect credentials. Rate tiers are exchange-specific; this application does not assume an authenticated quota. It serializes manual refreshes, spaces connector requests by at least 300 ms, and respects Retry-After.

### Canonical data and calculations

`OrderBookInstrumentId` includes exchange, catalog-native market ID, native instrument ID, and outcome label. For Polymarket, only stored aligned outcome/token pairs with decimal-digit token identifiers are addressable; missing or duplicate token mappings cannot be inferred. For Kalshi, `yes`/`no` are side identifiers scoped to the ticker, not invented token IDs. Only catalog classification `binary` plus complete Yes/No outcome metadata permits complements. Scalar, unknown and existing `Multivariate` classifications retain native bids and opposite bids, but have no executable asks. Existing catalog classification does not retain the underlying binary type for MVE; support is deliberately conservative until that metadata is available.

An immutable snapshot retains full returned levels (maximum 20,000 per side), retrieval UTC, separate optional source time/hash, native source market identity, validity, warnings and completeness (`FullReturnedDepth`). This means all levels of that bounded REST response, not global market consistency or a sequence-safe feed. Financial strings parse directly to decimal with invariant culture, no exponent/locale/NaN conversion or floating point. Oversized or excessive-precision strings are rejected rather than rounded. Kalshi accepts price scale up to four places and quantity scale up to two; these are current fixed-point fields, not integer-cent fallback. Canonical prices use payout units in [0,1]. Per-market tick-grid validation, minimum trade sizing and order eligibility are not asserted by this read-only L2 estimator.

The single normalizer sorts bids descending and asks ascending, removes zero-size levels, and rejects negative sizes, illegal prices and side/provenance contradictions. Duplicate prices invalidate the snapshot: an L2 entry may already be an aggregated total, so summing repeated entries could double liquidity. Crossed books are invalid; locked books are conservatively invalid because matching/atomicity guarantees have not been established. Empty sides are valid and have no best price. Kalshi validates both native bid sides before deriving `1 - opposite bid price` with unchanged quantity; each derived ask is `DerivedComplement`. Native own-side and opposite-side bids remain reconstructible. A later loss of binary catalog metadata suppresses cached complements immediately.

`ExecutableDepth.Calculate` walks full asks for Buy and full bids for Sell. It reports requested/executable/unfilled quantity, gross notional, quantity-weighted VWAP over actual depth, best/worst consumed price, level count, snapshot ID/time, freshness, actionability and reason. Quantity must be positive. Full and partial depth are explicit; no-liquidity prices and VWAP are null. Default stale or failed-refresh results calculate zero executable quantity. Explicit diagnostic mode may inspect stale valid data but is never actionable; invalid/unsupported data cannot be calculated even diagnostically. Decimal overflow rejects the preview. No fees, minimum order compliance, payout, edge, profit, ROI, execution or strategy results are calculated.

### Cache, APIs and desktop

The backend singleton `OrderBookCache` is thread-safe and bounded to 128 instruments by default (`Local:OrderBookCacheCapacity`, range 1–1024). It evicts the oldest updated entry. Only the catalog service admits API refreshes; arbitrary unknown identifiers cannot create cache entries. Cached GETs do not allocate entries. Immutable snapshots replace atomically, older retrievals cannot overwrite newer books, invalid/failed refreshes preserve the prior accepted snapshot with separate failure time/code/retry metadata. Restart creates an empty cache; SQLite catalog storage is unchanged and no migration/history table is added.

`Local:OrderBookFreshnessSeconds` defaults to 5 (validated 1–60). `TimeProvider` computes local retrieval age; backward/future clock ages are non-actionable. This is a conservative manual diagnostic threshold, not a trading-quality claim. Source timestamps and catalog retrieval age remain separate; fetching a book never refreshes catalog metadata. `BookEligibility` is the shared actionability predicate and latest refresh failures disable it.

Authenticated workspace routes under `/api/v1/workspaces/{workspaceId}/orderbooks/{exchange}/{marketId}`:

- `GET ?instrumentId=...`: cached state plus addressable instruments; omission selects the first stored addressable outcome.
- `POST /refresh?instrumentId=...`: one explicit selected-instrument public GET with safe retries. Global admission allows one refresh at a time, returns 409 when busy, and has no unbounded queue.
- `POST /depth` with `{ "instrumentId": "yes", "action": "Buy", "quantity": 25, "diagnosticOnly": false }`: cached gross estimate, no implicit refresh.

Every route checks authenticated workspace membership before catalog lookup/cache access. Unknown catalog market is 404; mismatched instrument or invalid input is 400. No token is accepted without a known catalog mapping. Read/depth paths make no external requests. Unsupported/not-addressable, validity, freshness, last refresh failure, and retained prior snapshot are distinct response concepts.

Dedicated public HttpClients use the existing handler with redirects/proxies disabled and ordinary certificate/hostname validation. Timeout is 12 seconds per HTTP operation within a 15-second source budget, payload is capped at 2 MB both by declared length and streamed bytes, and at most two safe GET attempts are made. Retry-After beyond the small local retry allowance is returned as a failure with retry time. Errors distinguish access denial, rate limits, timeout, secure connection, transport, JSON/envelope, malformed book, and unsupported structure. Clients bearing auth headers are rejected before sending. No raw payload or credential is logged.

Market Explorer displays an outcome selector, explicit Refresh Order Book, local state/age/source/retrieval timestamps, BBO/spread, native/derived labels and first ten levels per side. Full depth stays available to the backend calculator. Optional depth-entry UI is deferred; the authenticated preview API is implemented. No navigation, catalog notification or header Refresh initiates public orderbook traffic. A local display timer updates age without HTTP. Selection, access generation, workspace, backend instance and active state guard results; cancellation/disposal settle Loading and prevent late restoration. Backend instance changes clear old snapshots. Cancellation reaches the service/source safely because these are bounded read-only requests, not accepted long-lived jobs.

Phase 02B.2 may provide sources feeding this canonical immutable model/cache, but must add explicit sequence, reconciliation, subscription and reconnect semantics. Exchange credentials, order submission, paper fills, scanning and arbitrage detection remain absent.
